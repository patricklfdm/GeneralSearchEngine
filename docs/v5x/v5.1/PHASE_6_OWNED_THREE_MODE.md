## One request, one immutable source

The new `--three-mode` qualification uses the existing owned Runner, one budget
reservation, one lease and the same three instance/data-volume intents. Package
installation happens once per node; later modes reuse the exact completed
endpoint/descriptor and original preparation deadline. A failed or uncertain
installation stays consumed. Mounted-volume/provider/SSH identity rechecks still
run at each mode's preparation, transfer, sealing and service-launch boundaries.

Only the first published V4.4 guest prepares a source backup. The controller
retrieves that original export over authenticated bounded binary download, checks
its inventory and independently decodes its backup/checkpoint/metadata against
the frozen initial rich state. Later modes copy those exact three source files;
only their fresh group ID and topology descriptors differ. The source is checked
again before every export. It is never regenerated by another JVM. Receiver
transfer claims are keyed by the authenticated mode as well as the existing
package/node binding; each mode's partial claim remains consumed.

All seven idle services are prepared under the same 600-second stage. Each
receiver invokes the public bootstrap itself and keeps only its own authority at
the sealed live path. The Python service processes may coexist; voter JVMs from
different modes must not overlap.
