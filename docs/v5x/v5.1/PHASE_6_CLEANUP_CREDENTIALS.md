## Credential path

The integrated entry connects the existing context/run binding, credential
exchange, bounded provider HTTP, native cleanup policy and shared reconciliation:

```text
exact manual/scheduled entry and run attempt
  -> selected external-account descriptor
  -> GitHub OIDC claims checked against that entry
  -> Google STS exchange
  -> impersonate the selected cleanup service account
  -> existing scoped GCS/Compute requests
  -> retained lease/operation/ID reconciliation
```

[cloud_cleanup_credentials.py](../../../scripts/v51/cloud_cleanup_credentials.py)
accepts the external-account descriptor shape generated by the already pinned
[Google auth action](https://github.com/google-github-actions/auth/blob/7c6bc770dae815cd3e89ee6cdf493a5fab2cc093/src/client/workload_identity_federation.ts).
It binds the provider audience, exact service-account impersonation endpoint,
GitHub token source URL, request authorization header and JSON token format.
Extra credential kinds, keys, executable/file sources, delegate accounts, foreign
accounts/providers and alternate endpoints fail before credential traffic.
There is no ambient ADC or active-gcloud-account fallback.

The GitHub token request uses the selected provider's audience. Its returned JWT
must match repository name and numeric IDs, master ref, workflow and source SHA,
manual/scheduled event, environment, run ID/attempt and token validity. These
[GitHub OIDC claims](https://docs.github.com/en/actions/reference/security/oidc)
are checked again on every refresh. Local JWT decoding is **not signature
verification**: Google STS must authenticate the signed subject token and apply
its configured trust condition. The offline issuer cannot establish that trust.

The [STS exchange](https://docs.cloud.google.com/iam/docs/reference/sts/rest/v1/TopLevel/token)
uses the selected WIF provider, JWT subject type and access-token result type.
Only the resulting federated credential is sent to the fixed
[service-account impersonation endpoint](https://docs.cloud.google.com/iam/docs/reference/credentials/rest/v1/projects.serviceAccounts/generateAccessToken).
The requested account credential uses the cloud-platform scope and a 3600-second
maximum lifetime. Only that account credential reaches Compute/GCS. No keys or
additional IAM grants are required by this implementation.

## Bounds and failures

All three credential requests share one monotonic deadline capped by the original
provider request's remaining time. Responses remain size bounded, redirects are
forbidden by the existing network transport, and failures retain fixed diagnostic
categories without response bodies, subject/access tokens or credential URLs.

The account token's returned expiry becomes a monotonic cache limit, with a
60-second refresh margin and the existing 2400-second maximum cache age. A shorter
returned lifetime is respected. Invalid or expired credentials cannot reach the
provider. Existing string credential providers retain their prior cache behavior.
A provider GET receiving 401 can refresh once within its original deadline;
mutating requests remain once-only, including 401 or a lost response. Later
reconciliation recovers state through original operations and numeric resource IDs.

The existing cleanup policy still checks each request before credential acquisition.
Expiry/grace, retained ownership, generation conditions, original insert operations,
exact numeric deletion, immutable completion and terminal accounting remain the
only resource-deletion authority. Credential success does not bypass those checks.
A failed attempt's charge remains retained.

## Qualification and activation boundary

The existing provider gate now includes seventeen credential integration tests and
an additional 28 fresh-process cases: the fourteen retained cleanup cases through
both manual and scheduled entries, each using the complete credential exchange.
The original 28 entry cases and native/fake policy matrices also remain enabled.

The new matrix independently checks final HTTP state, absence, numeric deletion,
unchanged active/blocked records and preserved charges. It additionally requires
OIDC -> STS -> impersonation order and confirms that every provider request uses
the selected account token. Retained diagnostics contain only stage names,
timeouts and request counts. Unit negatives cover descriptor/claim drift, expired
credentials, denied exchanges, refresh, shared deadlines, forbidden request scope,
lost-delete reconciliation and early live-transport rejection.
