## Continuous GSLR state

Old voters start from independently derived bootstrap learner ledgers. The joining
owner starts at revision zero from its original old-majority seed, retaining the
original confirmation and endpoint obligations. The seed and initialized bytes
must match the already derived original initialization transaction.

Each retention round derives the local and remote successor from the preceding
continuous ledger and the original current generation. One exact write, force,
rename and parent-force chain must finish before its original ACK callback. The
remote ACK's revision and digest must match those derived bytes. Head confirmation
uses the original delivered query/ACK and preserves older obligations as renewals
before the durable confirmation return.

Every selected installation binds the exact local before-ledger to its installed
intent and all included frozen learner sources. Confirmed progress may discharge
older debt only through the existing independently derived selected merge. If the
plan changes, one new revision and one completed force chain are required after
generation installation and any peer completion, before learner completion and
the install return. A no-op consumes neither a write nor a completion callback.

All grant captures are compared to the current derived ledger. Publication and
FINAL adoption preserve it, and each retaining reopen must force the exact same
bytes after current-generation recovery and before peer-ledger recovery. Cold
snapshots must equal the continuous terminal state. Every regular write, completion
and recovery callback is consumed exactly once; unknown events fail closed.

## Separate admission custody

The first learner admission has an eleven-event `LEARNER_RETENTION_*` sequence
for its original custody record. It is not a voting owner's GSLR revision. Its
exact scope and owner must match, and it must finish after the admission plan and
before replica creation. Original custody bytes and initialization force sequences
remain independently checked by the physical prerequisite. This distinction avoids
counting the custody rename as a ledger update or silently discarding it.
