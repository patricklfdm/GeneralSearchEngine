# Phase 3 — profile-bound joining placement and initialization

The placement, custody retirement and native initialization readers now use the
explicit `3-ADD`, `4-ADD`, `3-REPLACE`, `4-REPLACE` or `5-REPLACE` profile. This
extends the [publication/old-voter prefix](PHASE_3_JOINING_PROFILE_PHYSICAL.md)
through the original joining owner's first retaining reopen and repeated basis.
The aggregate returns **PARTIAL**. Continuation, later adoption/installation,
complete control attempts, maintenance/peer chains and process recovery remain
separate qualifications. No runtime Java, workflow, workload or budget changes
are part of this batch.

## Independently derived storage

Expected placement bytes start with the public bootstrap and derived old-owner
history. The published source uses each publisher's actual collected checkpoint
ACKs, including a sufficient old-only pair in `3-REPLACE`. The joining identity
comes from the explicit profile and independently reduced catalog. Old node-4
therefore cannot become joining node-5 or node-6 by position or label.

The reader reconstructs the prepared learner, pending INTENT and forced joining
ACK, dormant generation, original inode-bound custody and exact atomic moves.
Retirement derives the predecessor deletions and resource reservations before
checking native ownership. Later mutable initialization files are checked in
their own stage, rather than treated as initial custody inputs.

Initialization consumes every original old-majority head exchange in canonical
owner order. It preserves the former endpoint as renewal debt, adds only the
actual joining copy to the peer plan, retains every old identity in JOINT, and
derives all original old PREPARE sources. The old majority has two owners at
size three and three owners at sizes four/five. The joining seed and all three
revision-zero ledgers are derived from those sources. Exact native families,
the first grant, repeated basis and reserved counter are then compared.

The three local force lifetimes belong to the actual joining identity. Missing,
reordered or foreign-owner initialization/grant observations are rejected.
Head exchange bytes and local force order are scoped checks; they do not claim
complete cross-node delivery or terminal observations for every control attempt.
The previously retained unanswered `FUTURE_RETENTION_INTENT` attempts remain
outside full network qualification.

## Original-first rejection checks

```bash
python3 -B -m scripts.v53.joining_profile_initialization_evidence /path/to/raw \
  --profile 3-REPLACE --qualify
```

The same entry point accepts each of the five profiles. It derives the prefix
once for each original or disposable history and checks placement, retirement,
then initialization. All three original stages must pass before any mutation.
Twenty-one disposable mutations must pass their earlier stages and fail the
designated stage with its exact declared reason. A broken prior stage or an
unrelated exception cannot count as successful rejection.

Cases alter custody identities, moved manifests, old reservations, live
deletions, joining seed/ledger debt, native grants/images/counters and local
force order. Mutations refresh the copied inventory hashes where applicable;
internally consistent metadata cannot replace the independently derived bytes.
The original inventory is checked again after validation and negative replay.

Conditional tests exercise all five profiles: third-owner head handling,
missing/extra/reordered heads, preserved removed-node debt and distinct old/new
node identities. Their compact callback fixture is a projection for reader
regression only. Changing its node labels does not create a native execution
for another profile.
