# Native maximum application image and physical reservations

Status: locally qualified. This batch keeps the 1.3 resource contract and
production code unchanged. It exercises the actual native export boundary through
public offline provisioning and local storage; it does not enable a public runtime.

## Actual boundary

The image container is limited to 64 MiB. The existing native backup writer counts
its original 32-byte request ID in the same backup budget before image normalization
removes that administrative value. The largest image generated by this route is
therefore **67,108,832 bytes (64 MiB minus 32 bytes)**. Its original three backup
members plus the 24-byte container overhead exactly consume 64 MiB.

`V53MaximumApplicationTest` calibrates the real core format with 1,024 typed
documents, an equality index and application sequence 41. The first 1,023 encoded
documents each occupy the full 65,536-byte document allowance. The last document
fills the remaining native export budget. No invalid padding or opaque bytes stand
in for application state. Exporting one additional document byte is refused with
CAPACITY_EXCEEDED and leaves the original backup unchanged. A container exceeding
64 MiB is separately refused before scratch creation.

This does not establish that every structurally possible 64 MiB container can be
exported by the native writer. The unsuccessful first calibration attempt tried
that larger normalized size and correctly hit the original backup budget; its
source map, failure log and raw calibration image remain retained.

## Storage route and independent evidence

Five voters are provisioned from the verified backup with a new history. Their
initial admissions and immutable bootstrap result stay unchanged. Actual local
PREPARE/SELECTED/installation, two certified BARRIER publications and two subsequent
campaigns retain complete source/generation snapshots. Each step reopens the
exclusive owner, and maintenance releases the exact obsolete generations, sources
and floor copies before the next step.

The first floor reaching seven application reservations retains a complete owner
snapshot before retirement. The reader derives its three governing copies from
the independently replayed installed generations. It checks all seven physical
image paths, full image lengths, distinct nonlinked files, exact floor bytes and
force order. SOURCE metadata contributes to staging as well as metadata; JOURNAL
and MISC retain their full existing reservations. Equal image hashes do not reduce
the physical copy count. The final typed read must preserve all documents, index,
new history and sequence 41, and all resource leases must close.

The shared independent image reader checks real core checkpoint, metadata and
manifest CRCs, profile, codec, bounds, document order, application sequence and
content identity. Its table-based Castagnoli checksum is checked against the
independent bitwise implementation and standard check value. Existing admitted
cross-view evidence is replayed after extracting that reader.

Original full evidence validation precedes targeted negative mutations. The latter
exercise image/history/sequence/document/CRC, physical copy count/size and receipt
scope components without making dozens of redundant multi-GiB copies. They are
component mutations after full physical replay, not new Java fault executions.

Retained work directory: `target/v53-max-application/`. The complete Java fixture
passes (one test, 4,111.378 seconds); 26 focused Python tests pass in normal and
optimized modes. Full independent replay and all 13 original-first negatives pass
in normal, optimized and archive-unpacked executions. The reader derives
469,761,824 physical image bytes, 469,840,132 staging bytes and 35,771,824 metadata
bytes at the seven-image peak, with 16 leases subsequently released by the owner.
The [source/build-bound index](phase2-evidence/maximum-application.json) retains
JUnit, reader results, failed attempts, the full portable inventory and archive
hashes. The original runtime is bound to the retained 709-class inventory and two JARs
from the publication-capacity batch. The maximum producer class snapshot is also
compared with the isolated fresh build; shared workspace target output rewritten
later is not substituted for these original artifacts.
The five-owner fixture runs in one JVM and requires the existing maximum-image
test setting `-DargLine=-Xmx4g`. A later attempt accidentally used the ordinary
small-regression `-Xmx1g` setting and exhausted its heap while copying the first
governing floor. Its unchanged sources, partial raw evidence and actual OOM dump
are retained separately; that attempt is not accepted evidence. This test-process
heap setting is distinct from each owner's unchanged disk/staging reservations.
Original authorities and typed scratch stay on Linux; only retained copies and
portable archives may use the external evidence disk.
The first independent replay exposed a reader layout error: `current()` validates
the selected generation manifest separately and returns only its member files.
The maximum-floor reader now copies that exact original manifest alongside its
members, retaining selector/digest checks. A small real-format regression verifies
selected versus inactive generations and rejects a stale manifest before any floor
construction. The failed replay and reader source are retained; the successful Java
run is reused without rewriting its raw evidence.

This batch does not qualify maximum capsule metadata, process death with large
images, network liveness, automatic scheduling or power loss. Phase 2 remains open
until its remaining integrated storage and closure audit obligations are satisfied.
