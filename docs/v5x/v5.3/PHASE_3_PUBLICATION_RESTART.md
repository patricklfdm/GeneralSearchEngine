# Phase 3 — acknowledging an original publication after receiver restart

This batch restores the incoming acknowledgement path from the actual native
owner after publication has selected a durable generation. Losing the old
in-memory campaign scope must not make that completed result unacknowledgeable.
It does not enable public membership or autonomous operation scheduling.

## Native authority

The existing activation endpoint accepts an exact PUBLISH for its current
completed publication without creating an activation round. The journal obtains
the original certificate, selection, ballot, parent voting view, published anchor
and generation from its verified native generation. No caller-supplied expected
hash, application-complete claim or historical observation reconstructs authority.
Native open first completes covered staging retirement and future-retention
promotion. A pending certificate alone cannot enter this acknowledgement path.

The request must match the original governing view and ballot, original proposer,
permanent identities and certificate. The original voting set remains the request
authority even when an INTENT or FINAL has changed the current configuration.
This grants no new vote or public-service eligibility to a removed member.
The owner and promise are checked again at ACK return; a higher observed ballot,
new selection, changed current publication or closed owner refuses the request.

The resulting PUBLISH_ACK has the same existing A06 format and exact generation
binding as the first attempt. Duplicate acknowledgements neither reapply the
application nor acquire new remote checkpoint observations. No new disk/wire
format, resource ceiling or retry budget is introduced.

## Qualification boundary

The original implementation fails the new real TCP close/reopen regression.
Local tests additionally cover pending-certificate refusal, altered certificate,
foreign sender, higher-ballot fencing and original-view acknowledgements through
an explicitly driven four-to-three REMOVE history. The cross-view check is a
Java component qualification, not complete joint-protocol independent acceptance.

Fresh receiving JVMs are interrupted with halt and SIGKILL at selector force,
future-retention promotion, publication completion and immediately before ACK.
The original sender's finite dispatch exhausts its I/O attempts while that receiver
is absent. After a new receiving JVM opens the same native storage, the test
explicitly resubmits the exact request twice. This is not a claim that the
automatic owner has already implemented restart reconciliation or unlimited retry.

The independent reader derives bootstrap, original votes, application ends,
future proofs, actual checkpoint transfers, interrupted files, completed recovery
and exact returned ACKs. It validates the original before applying mutations;
negative evidence cannot turn an already-invalid original into a passing result.
The [source-bound receipt](phase3-evidence/publication-restart.json) records
completed validation and retained failed attempts. Eight process cases use sixteen
fresh JVMs and four live-lock probes. Their original-first reader rejects 88 exact
mutations and passes after archive relocation under optimized Python. The earlier
cross-view fixture failed because its default adoption callback discarded native
provenance; the final fixture preserves the original owner's verified capsule and
ancestry and completes the removal, new stable barrier and operation retirement.

Autonomous publication reconciliation, incoming native ACCEPT/PROOF/application
controls, automatic election/discovery/maintenance, ADD/REPLACE learners, all seven
joint profiles, maximum completion headroom and full 3B–3E qualification remain
open. Existing finite transport retries and original operation deadlines remain
unchanged. No protected CI, public runtime, paid cloud or V5.2 Runner change.
